# 真实案例：试点客户还是公开发布

以下为本次贾诩最终方略原文，保留其措辞。这是单次公开案例，非通用效果基准。

---

**先做受限试点，第一周就同步寻找原有三家之外的客户；六周内不把完整公开发布列为必做项。** 两周的文档与自助安装投入，必须由实际交付中的重复障碍来证明必要性。

三家的关键分歧，是何时允许证据兑换成下一笔投入。战略家的两周关口够早，却允许口头购买意愿放行；陰谋家的实际收款更硬，却把外部验证留得太晚；纵横家指出采购速度不等于需求强弱，但没有解决团队只能活用六周的约束。我的裁断是：**尽早收交易证据，同时尽早引入局外人；采购尚未完成可以解释证据不足，不能批准继续垫资。**

具体执行：

1. **前三天，选一个核心任务，核实验证周期。** 分别问清三家的任务频率、现有替代办法、预算批准人和最早采购时间。选择原型已经能够解决、六周内有机会重复发生并完成购买的用途。至多接两家，统一范围、报价和验收条件。若只有一家符合，就把它当作待验证假设，找到第二个独立需求前不追加功能开发。

2. **第一周就招募局外客户。** 用简短说明、演示和明确报价定向接触同类买家，无须等待公开发布。验证的是对方愿不愿按同样条件进入真实使用，而非是否赞同产品理念。争取第三周开始交付，让后半程留给重复使用与购买。

3. **第二周末决定是否追加开发。** 至少一家已用现有核心流程完成真实任务，并按事先确定、能够覆盖交付与持续支持成本的价格实际付款；第二家已接受相同边界并安排真实使用，才继续投入。象征性小额付款不放行。采购延迟、负责人无权、合作信任不足要分别记录，但未过关就停止该假设的追加开发，不延期免费代劳。

4. **第三至六周验证复制，只修已出现的交付障碍。** 每家安装、配置、培训和支持都计入工时，按团队可持续承担的人工成本核算；共享功能也必须过这道账。仅补充能明确减少重复劳动的文档和自动化，不预留整整两周做发布建设。客户自己的真实操作才算使用，团队代办不算。

六周结束，继续投入的门槛是：**至少两家独立客户，其中一家来自原有三家之外，为同一核心用途实际付费，在多个自然发生的任务周期中重复使用；相同报价能够覆盖支持成本，新增交付无需专属开发。** 未达到，就不批准扩大投入。把“需求被否定”与“采购或观察尚未完成”分开记录，但两者都不能冒充成功。

**最脆弱的一环，是这个市场的购买与使用周期能否装进六周。** 若真正有价值的客户普遍采购缓慢、任务低频，这套方略会错过好市场。因此前三天必须先核实周期；若明显装不下，就承认当前资源无法取得所需证据，停止承诺六周验证成功。不能靠降低付款标准或把一次使用称为持续需求来补救。
