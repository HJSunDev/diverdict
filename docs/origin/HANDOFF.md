# 交接文档 · 策略合议产品

> 用途:让没参与过前面讨论的人(或智能体)接手本项目。
> 只记需求演进、核心判断与已定的边界。**产品内容本身不在此文,以 `advisors.md` 为准。**

---

## 一、产品是什么

一句话:**一套接入任意 AI 智能体的"决策评审团"制度**——用户提出一个重要决策问题,产品让三个正交视角各自独立给出方略、互相质询,最后由一个合议者收敛出最优解。

用户的最初描述是一个层级化的规划需求(人生→职业→工作→生活细节),任何层级都可以用这套多视角合议来做策略。讨论中把本质提炼为:**用户买的不是"三个角色聊天",是"不让单一视角的盲区杀死我"**。分歧(而非共识)才是产品提供的信息。

## 二、贯穿全程的第一原则:留白 / 相信模型

这条原则被用户的两次纠正反复加固,并穿透了产品的三层,**接手者若只记一条,记这条**：

- **提示词层**:只告诉模型"他是谁",一字不写"他怎么想"。限制是对模型上限的封顶,模型越强留白产出越好。
- **流程层**:不设动态分支(不让合议者判断"要不要再讨论一轮")。一个永远回答"是"的决策不是决策,是假装成智能的复杂度。
- **宿主层**:只陈述不变量(必须满足什么),不规定机制(用子代理还是命令行),不设防作弊机关。规则清楚完整,遵守规则交给智能体的理解力。

推论:产品内部**不内置任何智能**(零模型调用、零 API key),智能 100% 来自宿主。因此产品无过期部件,随模型与智能体集体进步自动增值。

## 三、核心判断(已定,不再讨论)

| 判断 | 理由 |
|---|---|
| 形态是 MCP Server(能力),不是专用智能体 | 目标是任意智能体接入,接入成本 = 一行配置 |
| 三家并行调用且上下文互相隔离 | 同一对话内串行扮演会锚定、趋同、平均化 |
| 三家使用同一个模型 | 模型路由是把"视角差异"这个核心资产外包给厂商偶然差异;且用户不信任跨模型质量 |
| 真实差异来自提示词对视角的提炼 | 世界观、所信、所看,而非流程清单 |
| 流程固定三拍:出策→质询→收敛 | 见 advisors.md |
| 第二轮必须是"质询"不是"讨论" | 讨论让分歧趋同,质询让分歧磨利,而趋同正是产品要防的 |
| 合议者必须直接给出最优解 | 产品定位:智能=替用户收敛出答案,不把分析推回给用户 |
| 隔离是产品的命门 | 若三家在同一上下文连演,核心价值即死亡 |

## 四、已否决的方案(接手者极可能重新提出,先读这里)

1. **三家路由到不同模型** — 否决:能力类型各异、质量不可信、差异来源错位。
2. **重提示词工程**(必答清单、锁死输出 schema、"不答完不许出结论") — 否决:是给当前模型缺陷打的补丁,会随模型进步变成枷锁。
3. **产品自带模型调用/用户自配 API key** — 否决:那样产品又成了一个智能体,违背"纯制度"定位。
4. **动态流程**(合议者判断是否打回重议) — 否决:有价值的场景里答案永远是"打回",故不做决策做成铁律。
5. **循环到达成共识** — 否决:共识是委员会的终点;本产品的哲学是带着分歧做决断。
6. **讨论式第二轮** — 否决:见上表"质询非讨论"。
7. **防偷懒机关**(要求宿主自报用了什么隔离机制) — 否决:把宿主当嫌疑人,是用不信任修不信任。
8. **把"二级信息"这个分层概念写进文档** — 否决:那是内部讨论用语。各家后半段的补充指引直接跟在身份定义后,无标签无解释。
9. **把具体年份数字写进指引**(如"十年后") — 否决:损害通用性。

## 五、文档地图 · `advisors.md`

按顺序,各节用分隔线隔开，**只保留核心信息**:

1. **四位角色的身份定义** — 战略家/纵横家/阴谋家/贾诩的提示词正文。**产品的核心资产,唯一值得反复打磨的部分。** 若某家"味道不纯",修法只能是更准确地说出他是谁,不是告诉他怎么想。
2. **流程与纪律** — 三拍流程 + 质询轮的防趋同三纪律。
3. **〔标记:不知道怎么说〕最优形态(终态目标)** — 前提为宿主提供受控隔离生成原语,单工具纯编排。**脱离现实的推演,不驱动实现决策。**
4. **〔标记:不知道怎么说〕最终判断:隔离生成的必然形态** — 对 Agent 厂商未来会交付"枷锁版隔离生成"(五道锁)的预判。**非落地依据。**
5. **当前可落地的最优形态:意图指令 + 宿主自选执行** — **落地方案。** MCP server 多工具状态机,每幕下发提示词 + 三条不变量规则(互不可见/无工具/同模型),机制宿主自选。附 CLI-as-API 强化路径与三形态递进关系。

优先级:第 1、2、5 节是落地依据;第 3、4 节带标记,属远期推演,参考但不驱动决策。

## 六、现状事实与待办

**已核实(2026-09-19)**:主流编程 Agent 普遍不支持 MCP sampling 这一"借宿主模型"的协议能力——Claude Code 官方 MCP 文档未提;Codex 只实现 tools;OpenCode 有未关闭的缺失 feature request(issue #28567)。支持 sampling 的主要是 Cline、VS Code Copilot 等编辑器系客户端。**注意:此结论需定期复核,它在缓慢变化。**

**未验证**:Cursor、OpenClaw、Hammers 等的 sampling/子代理/无头模式支持情况,当时未能查到可靠依据。

**待办**:

1. 质询轮的提示词措辞(如何让同模型真的攻击而非客套) — 提示词工程剩余的最大一块。
2. V1 实现:`advisors.md` 第 5 节的多工具状态机 MCP server。工程上是纯字符串拼装 + 状态推进,无模型调用;提示词从 `advisors.md` 载入。
3. 实测:三家产出是否真有差异、质询是否真在攻击、合议是否真能收敛——这是产品成立与否的唯一验证标准,靠实测打磨。
4. 首发宿主选择:体验优先(只做有无头模式的宿主,走进程级编排)vs 覆盖优先(纯意图指令适配所有宿主)。

**已明确砍掉(V1 不做)**:人生/职业/工作四级规划体系、记忆与决策日志、任何 UI、多阵容/lens pack 可配置。

## 七、协作偏好

- 站在产品本质和取舍的角度思考,主动指出过度设计;该砍就砍干净。
- 保持"少"。任何为了"更可用、更稳妥"而加回来的机制,先问它是不是在给用户当前不存在的麻烦打补丁。
- 区分耐久资产与折旧部件:提示词内容和流程纪律是资产;适配层、约束脚手架、兼容兜底是折旧件,写了就要按"将来整体删除"来设计。
- 修改需明确指示。讨论与落盘是两件事,没让改文档时不要改文档。
